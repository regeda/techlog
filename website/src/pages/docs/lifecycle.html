Lifecycle Model

Proposed · draft 0.1Illustrative examples

The chain

A change usually travels from a problem to a follow-up. Each stage is recorded as one or more events, and each event links back to the one before it. A stage can be skipped (a hotfix may have no proposal), and a story can loop (an incident may lead to a new change).

flowchart LR
  subgraph BUILD[Build and ship]
    direction TB
    P[Problem] --> PR[Proposal] --> D[Decision] --> I[Implementation] --> V[Verification] --> R[Release]
  end
  subgraph RUN[Run and learn]
    direction TB
    PROD[Production] --> INC[Incident] --> M[Mitigation / rollback] --> REM[Remediation] --> F[Follow-up]
  end
  BUILD == release reaches production ==> RUN

Two loops close the circle. An incident can point back to the implementation that is suspected of causing it, and a follow-up action can prevent the next release from repeating the failure.

Stages

Problems

Records a need, defect, or request. Typical type: problem.reported. It is usually the start of a story, so it has few links, or a relates_to link to a similar report. Recorded by a person, or collected from an issue tracker.

Proposals

Records a proposed solution and the alternatives. Typical types: investigation.completed and proposal.recorded. Links: investigates and motivated_by the problem. Often recorded by an AI agent on behalf of a person.

Decisions

Records what was decided, by whom, and on what terms. Type: decision.made. Link: decides a proposal. Recorded by a person, or by a chat or tracker integration after a person confirms it.

Implementations

Records the change itself. Type: change.implemented. Links: implements the proposal and relates_to the decision. Usually collected from a pull request or a commit, with the sources attached.

Verification

Records tests and checks, with the report as evidence. Type: verification.completed. Link: verifies the change. Usually recorded by CI.

Deployments

Records a version reaching an environment or a share of traffic. Type: release.deployed. Link: releases a change. Usually collected from a deployment system.

Incidents

Records that something broke. Type: incident.opened. Links: observed_after a release, and caused_by a change (often a hypothesis at first). Usually recorded by an alert or an incident tool.

Mitigations

Records a temporary measure that reduces impact, such as a feature flag. Type: mitigation.applied. Link: mitigates an incident or a problem. Recorded by a person.

Rollbacks

Records that a release was reverted, and then that recovery was checked. Types: rollback.executed and recovery.verified. Links: reverts the release, mitigates the incident, and verifies the rollback.

Postmortems

Records the review of an incident. Type: postmortem.published. Link: follows_up the incident. Usually collected from a document or recorded by a person.

Corrective actions

Records what will be done so the problem does not recur, and whether it was done. Type: action.tracked. Link: follows_up the incident or problem. Tracked until a verified outcome.

Confirmed relationships vs hypotheses

A confirmed link is drawn as a solid line, a hypothesis as a dashed one. A hypothesis is a suspected cause that nobody has established yet. It becomes corroborated when a new event is recorded, such as an investigation that finds the root cause, and that event links back to the same incident. Nothing edits the earlier event.

Worked example: Spring Spin

This simulated story follows a discount game for new clients in a service called promo-api. The ids are the real ids in the examples.

  1. evt_01J9K2A0P002 problem.reported: new-client sign-ups have been flat for three weeks.
  2. evt_01J9K2A0P004 proposal.recorded by an agent: a spin-to-win game, capped at 20%. Link: motivated_by P002.
  3. evt_01J9K2A0P005 decision.made: approved with finance. Link: decides P004.
  4. evt_01J9K2A0P006 change.implemented: the spin endpoint. Links: implements P004.
  5. evt_01J9K2A0P007 verification.completed: abuse tests passed. Link: verifies P006.
  6. evt_01J9K2A0P010 release.deployed: version 3.8.0 as a 5% canary. Link: releases P006.
  7. evt_01J9K2A0P011 incident.opened: 5xx ratio of 6.2%. Links: observed_after P010 (confirmed) and caused_by P006 (hypothesis).
  8. evt_01J9K2A0P012 rollback.executed: the canary returns to 3.7.2. Links: reverts P010 and mitigates P011.
  9. evt_01J9K2A0P015 investigation.completed: duplicate spins from retrying mobile clients. Links: investigates P011 and caused_by P006 (confirmed). The hypothesis is now corroborated by this event.
  10. evt_01J9K2A0P016 change.implemented: an idempotency key. Link: follows_up P011.
  11. evt_01J9K2A0P018 release.deployed: version 3.8.1 promoted to 100%.
  12. evt_01J9K2A0P022 mitigation.applied: a feature flag restores the old result panel for older browsers.
  13. evt_01J9K2A0P024 action.tracked: follow-ups, including a browser check before go-live.

Rules of thumb

  • Events are append-only. A correction is a new event, and the old one may be given the status superseded.
  • Links point backward in time, from the later event to the earlier one.
  • Prefer a hypothesis you can later confirm over a confident claim you cannot support.
  • Record evidence as references. The artifact stays in the tool that owns it.
