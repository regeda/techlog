Reliability Engineering

Proposed · draft 0.1Illustrative examples

Incident lifecycle tracking

An incident is a series of events: incident.opened, then mitigation or rollback, then recovery.verified, and often a postmortem. Each event has the status it had when it was recorded (open, mitigated, resolved), so the history shows how the incident moved rather than only where it ended.

Mitigation plans

A mitigation is a temporary measure, such as a feature flag or a traffic shift. It is recorded as mitigation.applied and linked to the incident it mitigates, so the permanent fix can later be tied to the same story.

Upgrades

An upgrade plan names the current and target versions and the stages between them. The change event that introduced the target version is linked to the plan, so a rollback decision can see what changed.

Canary progression

This plan, from the Spring Spin example, upgrades promo-api from 3.7.2 to 3.8.0 in three stages:

StageTrafficHoldHealth checks
canary-55%15 minutes5xx ratio below 1% over 3 minutes; spin p99 below 450 ms over 5 minutes
canary-2525%30 minutesSame checks
full100%NoneSame checks, then recovery verification

Promotion requires all health checks to pass for the whole hold, verification evidence on the change event, and no open incident on the service.

In-place upgrades

An in-place upgrade has no traffic split, so there is no small group of users to learn from first. Rollback triggers rely on health checks after the fact, and recovery depends on a path such as a snapshot or the previous artifact. This is riskier than a canary, and a plan for it should say so in its unresolved risks.

Rollback planning

A rollback plan has nine parts: current and target versions, stages, health checks, promotion criteria, rollback triggers, recovery steps, verification criteria, unresolved risks, and approvals.

Recovery verification

A rollback is not finished when traffic moves. The verification criteria say what to check afterward, such as the 5xx ratio staying below 0.2% for ten minutes. The result is recorded as recovery.verified and linked to the rollback.

Recurrence prevention

Follow-up work is recorded as action.tracked events and tracked to a verified outcome. An action that is only agreed has not prevented anything yet; it counts when a later event verifies it.

Worked example

The 3.8.0 canary of promo-api (evt_01J9K2A0P010) raised the 5xx ratio to 6.2%, above the 1.0% trigger. An incident was opened (evt_01J9K2A0P011), linked to the change as a hypothesis. The approved rollback plan was activated (evt_01J9K2A0P012), and recovery was verified (evt_01J9K2A0P013). An investigation found that retrying mobile clients sent duplicate spins (evt_01J9K2A0P015), which confirmed the hypothesis. The permanent fix, an idempotency key (evt_01J9K2A0P016), was replayed against recorded canary traffic and then released as 3.8.1 (evt_01J9K2A0P018). The prevention actions are tracked in evt_01J9K2A0P024.

Simulation vs. platform. Validating a rollback plan, for example by finding missing prerequisites, is a proposed capability. It is not implemented in this repository.
