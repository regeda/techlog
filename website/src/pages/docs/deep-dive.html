Event schema, precisely

An event has eight required fields: schema_version, id, type, time, actor, subject, status, and provenance.

  • id matches ^evt_[0-9A-Z]{12}$.
  • time is RFC 3339 in UTC, written with a trailing Z. Offsets such as +02:00 are not accepted.
  • additionalProperties is false at the top level and in each $defs object, so a misspelled field is an error rather than silently ignored.
  • Extension keys match ^[a-z0-9]+(\.[a-z0-9-]+)+$, for example org.techlog.code.

Identity and time

  • Ids are opaque. The recorder assigns evt_ plus 12 characters, and no ordering is implied by the id.
  • time is when the event happened, not when Techlog received it. A late-arriving event can carry an earlier time than events already stored.
  • Clocks differ between systems. Order within a story comes from links first and times second, and consumers should tolerate small skews.
  • A separate recorded-at timestamp is an open question (see the end of this page).

relates_toany → any, when no stronger relation applies

Rules:

  • A link points to an earlier event.
  • basis is confirmed or hypothesis. A hypothesis link must be a caused_by.
  • A hypothesis is corroborated by recording a new event that states the same link with basis: confirmed. The old event is never edited.

Example from the Spring Spin story: the incident evt_01J9K2A0P011 links observed_after the release evt_01J9K2A0P010 (confirmed) and caused_by the change evt_01J9K2A0P006 (hypothesis). The investigation evt_01J9K2A0P015 later states caused_by evt_01J9K2A0P006 with basis: confirmed.

Evidence and provenance

Evidence is a reference (kind and ref) and an optional digest of the form sha256: followed by 64 hex characters. The digest covers the bytes of the referenced artifact at collection time.

provenance.method is one of collected (pulled from a tool), agent_submitted, human_entered, or derived (computed from other events). confidence is asserted or corroborated. A collected event with a digest deserves more trust than an unsupported assertion by an agent, and the model keeps that difference visible instead of hiding it.

A story starts with problem.reported (the first state, Reported) and ends when follow-up actions are tracked (FollowedUp).

The diagram shows the common path of one story, not a constraint. Events may skip stages: a hotfix can go from a problem straight to a change, and the Spring Spin story loops back from an incident to a new change.

Policy evaluation order

  1. Match the trigger.
  2. Evaluate the conditions.
  3. Gather evidence by kind and status.
  4. Check approvals: the role, the count, and that the approver is not the actor who submitted the change.
  5. Apply exceptions, such as an unexpired risk acceptance.
  6. Produce an outcome: compliant, missing_evidence, approval_required, or blocked.
  7. Record an audit event with the inputs and the outcome.
  8. Hand the outcome to enforcement integrations, only if enforcement.mode is enforce_via_integration.

MCP tool contracts

These are the five implemented tools, as the server reports them. MCP integration lists the proposed ones.

{{code json mcp-tools.json}}
  • Idempotency. techlog_record_event should accept an idempotency key (proposed, not implemented), so a retried request records one event. Today a retry records a second event.
  • Errors. Implemented: a failure returns isError: true and a text block that lists each problem as a JSON Pointer path and a message. Proposed: a structured code and the offending field in structuredContent.
  • Pagination. Implemented: list-style tools take limit (search: default 20, at most 100; history: default 50, at most 200). Proposed: a cursor when more results exist. The web UI pages its event list with an offset.

An example error, for techlog_link_events called with rel caused_by and without basis:

{"isError": true, "content": [{"type": "text", "text": "Rejected. Fix these problems and call the tool again:\n- /: missing property 'basis'"}]}

Proposed validation checks; not implemented in this repository:

  • At least one rollback trigger exists.
  • Every stage has a health check that covers its signals.
  • Every recovery step has a verification.
  • Unresolved risks are acknowledged by an approver.
  • The target and current versions differ.
  • The plan references the change event.

Versioning and compatibility

  • 0.x-draft versions may break.
  • After 1.0, minor versions are additive only.
  • The core is strict: unknown top-level fields are rejected. Unknown extensions are ignored.
  • Deprecations come with a window before removal.
ChangeCompatibility
Add an optional fieldCompatible.

Integrity and threat-model caveats

A digest detects a change to a referenced artifact only if the digest was recorded honestly in the first place. Append-only storage is a design goal that still needs a concrete implementation.

No tamper-proof or guaranteed-compliance claim is made without a concrete implementation and threat model.

Open threat-model items:

  • Event forgery by a compromised agent or a leaked signing key (see signed events).
  • Replay of valid events.
  • Clock manipulation.
  • Evidence substitution after the digest is recorded.
  • Tenant boundary errors.

Conformance test outline

Proposed: JSON test vectors of valid and invalid events, link-rule checks, policy outcome vectors, and MCP schema checks. Producers and consumers would conform separately. None of this is implemented.

Open questions

  • Should there be a recorded-at timestamp in addition to the event time?
  • How should evidence be signed, and by whom?
  • Which signature algorithms are allowed, and how are events signed with a later-revoked key treated?
  • What does redaction mean for an append-only history?
  • How should an event that spans several systems be modeled?
  • Is the current id scheme the right one?
